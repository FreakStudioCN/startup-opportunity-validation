# 三人 + AI 假设验证实验系统 Execution Plan

版本：2026-08-21

输入文档：

- `Task.md`
- `关于AI+硬件产业机会假设的新思路和新思考.md`

本文件只做研究系统设计，不定义 Blockless 的产品形态，不开发完整产品，不把 AI 判断当成事实。

## 0. 执行原则

第一阶段目标不是“做一个全网爬虫 / SaaS / CRM / Agent 平台”，而是在 7 天内用最低成本验证：

> 互联网上是否存在可识别的 Qualified Hardware Demand，并且其中一部分是否愿意进入真实项目验证。

约束：

- 团队只有 3 人。
- AI 负责规模化信息处理：搜索、抓取、清洗、分类、聚类、摘要、草拟消息、草拟 RFQ。
- 人只负责关键判断、深度访谈、供应商沟通、报价确认、付款节点。
- 每个实验 1-3 天内必须有第一轮结果。
- 每个假设必须可证伪，必须有失败标准。
- 第一阶段不做 Web Dashboard、SaaS、用户注册、完整 CRM、完整供应商平台、完整 Agent 平台、完整数据库产品。

## 2. 公开数据验证 vs 访谈/真实交易验证

### 2.1 主要可用公开互联网数据 + 爬虫 + AI 验证

- H-A1：硬件需求是否大量存在。
- H-A2：需求是否来自非 Maker 人群。
- H-A3：是否存在未满足原因。
- H-A4：需求是否有真实问题/意图。
- H-B1：AI 是否促使用户开始尝试，公开数据只能验证“迹象”，不能单独证明因果。
- H-B2：AI 是否带来真实项目，公开数据可验证行动证据。
- H-C1：AI-assisted prototype 完成案例。
- H-C2：DIY 卡点类型和频率。
- H-C3：公开表达的外部帮助寻找行为。
- H-D1：公开互联网中 Qualified Demand 密度。
- H-D2：AI 识别 precision。
- H-D3：需求簇能否形成。
- H-E1：RFQ 生成质量的初步可行性。
- H-E2：供应商候选能否被搜索发现。
- H-G1/G2/G3 的部分过程成本可自动记录。

### 2.2 必须通过访谈 / RFQ / 真实交易验证

- H-B1 的因果确认：AI 是否真的改变了用户行动。
- H-C3 的真实下一步：用户是否真的愿意寻求外部帮助。
- H-C4：是否愿意把外部帮助交给新的连接方。
- H-E1 的最终有效性：供应商是否看得懂 RFQ。
- H-E3：供应商是否愿意接项目并报价。
- H-F1：客户是否信任中国连接方。
- H-F2：客户是否接受报价。
- H-F3：客户是否付款。
- H-G2/G3：真实容量和贡献毛利。

## 4. 每个原子假设的 Minimum Viable Experiment

### H-A1：全球存在大量硬件需求

假设：

> Reddit / GitHub / YouTube / Forums 等公开渠道中存在大量真实硬件需求。

验证方法：

1. 网站：Reddit、GitHub Issues/Discussions、YouTube videos/comments、HN、Discourse/论坛、搜索结果。
2. 关键词：
   - `"I want to build" hardware`
   - `"How can I make" sensor`
   - `"Looking for someone to build" prototype`
   - `"need a PCB" OR "need manufacturer"`
   - `"why doesn't someone make" device`
   - `"custom hardware" "too expensive"`
3. API/crawler：优先 API/RSS/搜索 API；遵守 robots.txt 和平台条款。
4. 字段：source、source_item_id、url、title、body、author、created_at、community、score、comment_count、matched_query。
5. AI 分类：is_relevant、is_hardware、is_demand、demand_type、problem、intent_level、confidence。
6. 去重：canonical_url + normalized_title hash + embedding similarity > 0.92。
7. 真实需求判断：有具体使用场景、约束、痛点、行动或询价信号。
8. 样本量：第一轮 10,000 条 raw items。
9. 周期：1-2 天。
10. 成立：>= 150 条 hardware demand signal，人工抽样 precision >= 60%。
11. 失败：< 50 条，或 top results 大多不是实体产品需求。

### H-A2：需求不是少数极客特殊需求

验证方法：

1. 输入：H-A1 中所有 demand signals。
2. 字段：author_profile、community_type、language_markers、self_description、project_context。
3. AI 分类用户类型：maker/engineer、startup founder、small business、researcher、creator、consumer、unknown。
4. 人工抽检：每类抽样 20 条。
5. 样本量：至少 300 条 demand signals。
6. 成立：非 maker/engineer >= 30%。
7. 失败：>= 80% 来自工程师/Maker 社区，普通用户信号稀少。

### H-A3：需求有明确未满足原因

验证方法：

1. 输入：H-A1 demand signals。
2. 抓字段：why_existing_solution_fails、suppression_reason、quoted_evidence。
3. 分类标签：no_technical_skills、too_expensive、no_manufacturer、no_engineer、too_complex、not_important、just_idea、unknown。
4. 判断：只有前五类计入 suppressed demand。
5. 样本量：300 条 demand signals。
6. 成立：Suppressed Demand Ratio >= 25%。
7. 失败：大多只是“如果有就好”的轻度想法，未表达执行障碍。

### H-A4：需求是想要/问题/意图，不是脑洞

验证方法：

1. 输入：H-A1 demand signals。
2. Intent ladder：Idea、Interest、Problem、Intent、Purchase Intent。
3. AI 证据要求：必须输出原文证据片段，不允许只给标签。
4. 人工抽检：Top 200。
5. 成立：Intent 或 Purchase Intent >= 20%。
6. 失败：Intent+ < 5%，或人工确认大部分是娱乐讨论。

### H-B1：AI 让更多人开始尝试硬件

验证方法：

1. 网站：Reddit、GitHub、YouTube、Hackaday、论坛。
2. 关键词：
   - `"ChatGPT helped me build" hardware`
   - `"using AI to design PCB"`
   - `"AI helped me prototype"`
   - `"I asked ChatGPT" Arduino enclosure sensor`
3. 字段：ai_tool、pre_ai_state、post_ai_action、action_evidence。
4. 访谈：联系 5-10 个公开作者，确认“没有 AI 是否会行动”。
5. 成立：>= 30 个公开行动案例，访谈中 >= 3 个确认 AI 是关键触发因素。
6. 失败：AI 只是写文案/代码辅助，没有改变是否开始硬件项目。

### H-B2：AI 产生真实项目而非玩具创意

验证方法：

1. 输入：H-B1 案例。
2. 行动证据：GitHub repo、BOM、CAD、PCB 文件、采购截图、build log、询价、样机照片。
3. 分级：AI Idea、User Interest、User Effort、Real Requirement。
4. 成立：>= 15% AI 相关需求有 User Effort 或 Real Requirement。
5. 失败：大多停留在 prompt 输出或社交媒体展示。

### H-C1：用户可用 AI 完成早期 Prototype

验证方法：

1. 搜集 50 个 AI-assisted hardware project。
2. 抓字段：prototype_type、components、firmware_status、enclosure_status、working_demo_evidence。
3. 判断 prototype 完成：可运行视频/代码+照片/复现实验说明。
4. 成立：>= 20 个完成早期 prototype。
5. 失败：大多只有概念图或不可运行设计。

### H-C2：DIY 仍有 AI 无法解决的断点

验证方法：

1. 输入：H-C1 项目和需求评论。
2. blocker_type：PCB、SMT、enclosure、battery、waterproofing、EMC、certification、assembly、testing、supplier、cost、reliability。
3. AI 提取原文证据，人工确认 top blocker。
4. 成立：>= 30% 项目出现需要外部帮助的 blocker。
5. 失败：用户自己解决或卡点与制造连接无关。

### H-C3：卡住后用户会寻找外部帮助

验证方法：

1. 关键词：
   - `"looking for manufacturer"`
   - `"need someone to build prototype"`
   - `"where can I get this made"`
   - `"need PCB assembly"`
   - `"custom enclosure manufacturer"`
2. 字段：help_type、budget_signal、timeline_signal、contactability。
3. 成立：外部帮助寻找信号 / 卡住案例 >= 15%。
4. 失败：用户倾向放弃、等开源方案、或只找本地朋友。

### H-C4：用户愿意交给新的连接方

验证方法：

1. 从 H-C3 选择 30 个高意图用户。
2. AI 做背景研究：公开 profile、项目状态、可能需求、风险。
3. 人工审核后发送第一封消息。
4. 衡量：reply、call booked、requirements shared、permission to quote。
5. 成立：>= 5 个愿意继续沟通。
6. 失败：无人回复，或回复中明确不信任新的中国连接方。

### H-D1：公开互联网可低成本发现需求

验证方法：

1. 建立 MVP crawler，不做 dashboard。
2. 数据源：Reddit、GitHub、YouTube、HN、Discourse forums、Kickstarter/Indiegogo via search、public web search。
3. 输出：raw JSONL + normalized JSONL + demand_candidates.csv。
4. 样本量：10,000 raw items。
5. 成立：>= 10 QD / 1,000 raw items。
6. 失败：低于 2 QD / 1,000，或合规成本过高。

### H-D2：AI 能从噪声中识别值得跟进的人

验证方法：

1. AI 对 raw items 评分并输出 top 200。
2. 人工标注：qualified / not qualified / unsure。
3. 计算 Precision@50、Precision@100、Precision@200。
4. 成立：Precision@200 >= 60%。
5. 失败：Precision@200 < 30%，人工筛选成本无法接受。

### H-D3：AI 能发现需求簇

验证方法：

1. 对 qualified demands 生成 embedding。
2. 用 HDBSCAN 或层次聚类，先不做复杂调参。
3. 输出 cluster summary：共同问题、用户类型、现有方案缺口、外部帮助率。
4. 人工审核每个 cluster 是否“同一市场假设”。
5. 成立：>= 3 个 cluster，每个 >= 8 个 unique users，且跨 >= 2 个来源。
6. 失败：只能发现孤立需求，cluster 无商业共同性。

### H-E1：AI 能生成供应商可理解 RFQ

验证方法：

1. 输入：20 个高分 QD。
2. Agent workflow：
   - Extract user problem
   - Convert to structured requirement
   - Infer technical modules
   - Detect missing info
   - Generate clarifying questions
   - Draft RFQ
3. 人工审核：是否可发给供应商。
4. 成立：>= 10 个 RFQ readiness pass。
5. 失败：RFQ 过度猜测、缺核心参数、供应商无法理解。

### H-E2：AI 能找到匹配供应商

验证方法：

1. 输入：10-20 个 RFQ-ready requirements。
2. AI 生成中英文关键词、工艺关键词、同义词。
3. 来源：Alibaba、Made-in-China、1688、Google、供应商官网、行业目录。
4. 提取 Supplier Capability Schema。
5. 人工审核 Top 3。
6. 成立：>= 60% 需求找到 3 家候选供应商。
7. 失败：候选多为贸易商、能力不匹配、无法联系。

### H-E3：供应商愿意接项目并报价

验证方法：

1. 对 10 个需求各发 3 个 RFQ。
2. 记录：sent_at、channel、response、quote、MOQ、lead_time、questions、decline_reason。
3. 成立：30 个 RFQ 中 >= 8 个有效回复，>= 3 个报价。
4. 失败：供应商不回复，或普遍拒绝小批量/不完整需求。

### H-F1：客户信任中国硬件连接方

验证方法：

1. 联系 30 个高意图用户。
2. 信息表达：不是卖 SaaS，而是“可以帮你把需求转成可报价项目，并连接中国制造资源”。
3. 指标：reply rate、positive reply、call booked、requirements shared。
4. 成立：>= 5 个继续沟通。
5. 失败：信任阻力明显，无法进入需求确认。

### H-F2：用户愿意接受报价

验证方法：

1. 对 3-5 个经过访谈确认的需求给真实报价。
2. 报价包含：scope、deliverable、timeline、price、deposit、risk exclusions。
3. 成立：>= 1 个用户口头接受或进入付款。
4. 失败：用户认为报价不可接受，或只想免费咨询。

### H-F3：用户愿意付款

验证方法：

1. 对接受报价用户提出定金。
2. 不问 “Would you pay”，而是给出具体支付链接/合同。
3. 成立：获得 >= 1 笔定金。
4. 失败：所有用户在付款节点退出。

### H-G1：AI 降低人力成本

验证方法：

1. 每个需求记录阶段时间：Discovery、Classification、Review、Outreach、Interview、RFQ、Supplier Search、Quote。
2. 自动记录 AI/API/crawler 成本。
3. 成立：Human Hours / Qualified Demand <= 0.5h。
4. 失败：每条 QD 仍需 > 2h 人工。

### H-G2：三个人能处理足够项目量

验证方法：

1. 用 7-30 天漏斗推算月度容量。
2. 指标：Qualified Leads / FTE / Month、Quotes / FTE / Month、Paid Projects / FTE / Month。
3. 成立：单人每月可处理 >= 20 个 qualified leads 或 >= 3 个报价项目。
4. 失败：人工瓶颈太早出现。

### H-G3：单项目经济模型成立

验证方法：

1. 每个报价项目记录 Customer Payment、Supplier Cost、AI/API Cost、Human Cost、Shipping、Risk Reserve。
2. 公式：

```text
Contribution Margin =
Customer Payment
- Supplier Cost
- AI/API/Crawler Cost
- Human Cost
- Shipping
- Risk / Refund Reserve
```

3. 成立：Contribution Margin / Human Hour 高于团队机会成本，且风险可控。
4. 失败：毛利被沟通、返工、物流和风险吞噬。

## 5. MVP Research Crawler 设计

### 5.1 数据源判断

| Source | 方式 | 第一阶段建议 | 抓取字段 | 注意事项 |
| --- | --- | --- | --- | --- |
| Reddit | Data API / OAuth；也可先用搜索结果定位公开页 | 高优先级，但必须申请/遵守 API 规则 | post/comment id、title、body、subreddit、author、score、comments、created_at、url | 需要审批和 OAuth；不要无授权大规模抓取 |
| GitHub | REST Search API / GraphQL | 高优先级 | issue/discussion/repo、title、body、comments、labels、stars、updated_at、url | Search API 有速率和结果上限；适合公开开发者需求 |
| YouTube | YouTube Data API | 中高优先级 | video_id、title、description、channel、comments、published_at、stats | 评论抓取成本高；先搜视频和 top comments |
| Hacker News | Official Firebase API / Algolia HN Search | 中优先级 | story/comment、title、text、author、time、points、url | 硬件需求密度可能低，但技术创业者多 |
| Kickstarter | 搜索引擎 / 项目公开页 / RSS 如可用 | 中优先级 | project、category、funding、comments、creator、reward、url | 不作为直接爬取重点；用作需求簇/竞品信号 |
| Indiegogo | 搜索引擎 / 项目公开页 | 中优先级 | campaign、category、funding、comments、updates、url | 不做大规模直接爬；优先搜索引擎 |
| Maker/Hardware Forums | Discourse API / RSS / sitemap / robots allowed pages | 高优先级 | topic、posts、author、category、created_at、url | 选择 5-10 个具体论坛，不做全网 |
| Public Web Search | Search API / SerpAPI / Brave / Google programmable search alternatives | 高优先级 | query、title、snippet、url、rank、domain | Bing Web Search API 已退役；Google Custom Search 对新客户不可用，需选替代 |
| Common Crawl | Index API / WARC sampling | 低优先级 | url、domain、text snippet | 第一周不建议上，成本和噪声太高 |

资料核查注记：

- Reddit Data API 当前要求开发者遵守 Responsible Builder Policy，并可能需要审批与 OAuth token。
- GitHub REST Search API 支持搜索公开 items，但有速率、查询长度、结果上限等限制。
- YouTube Data API 提供 search.list 等官方接口。
- Hacker News 有官方 Firebase API。
- Google Custom Search JSON API 文档显示对新客户关闭，现有客户有迁移期限。
- Microsoft Bing Search APIs 已于 2025-08-11 退役。

### 5.2 第一阶段最值得使用的数据源

优先顺序：

1. GitHub Issues/Discussions：结构化强，开发者/硬件项目线索清晰。
2. Reddit：需求表达自然，覆盖非专业用户，但合规要求高。
3. Discourse/Maker forums：硬件问题密度高，很多卡点明确。
4. YouTube：build log 和评论中能发现需求/卡点，但评论成本较高。
5. Public web search：适合补充长尾和供应商搜索。
6. HN：用于创业/技术人讨论，不作为主需求池。
7. Kickstarter/Indiegogo：用于竞品和需求簇验证，不作为直接 lead 抓取主渠道。

### 5.3 不应该直接做的事

- 不绕过登录、反爬、付费墙或平台限制。
- 不抓取私信、个人敏感数据或非公开内容。
- 不把平台数据用于训练模型。
- 不做“全站全量爬取”。
- 不为了采集而建立复杂分布式爬虫。

## 7. Demand Score

评分不是事实，只是“优先级假设”。每个分数必须保留证据、置信度和人工抽检结果。

### 7.1 分项指标

| Metric | 定义 | 分值 | 数据来源 | LLM 判断方式 | 人工确认 |
| --- | --- | --- | --- | --- | --- |
| Problem Severity | 问题是否真实、频繁、造成成本/风险/效率损失 | 0-5 | 原文痛点、评论 | 提取痛点和影响 | Top 100 |
| Intent | 用户行动强度 | 0-5 | 询问、找人、采购、repo、原型 | 按 ladder 分类 | Top 100 |
| Urgency | 是否有时间压力 | 0-3 | deadline、ASAP、project timing | 提取时间词 | 报价前 |
| Existing Solution Gap | 现有方案为何不满足 | 0-5 | current_solution、complaints | 提取替代方案失败原因 | Top 100 |
| Suppression Reason | 是否被技术/成本/供应链压制 | 0-5 | why not built | 分类 suppression | Top 100 |
| Budget Signal | 是否有预算/价格讨论 | 0-4 | 金额、MOQ、quote、cost | 正则 + LLM | 报价前 |
| External Help Probability | 是否可能需要外部帮助 | 0-5 | help keywords、blockers | 判断 help type | outreach 前 |
| Manufacturability | 小批量制造可行性 | 0-5 | 技术模块/工艺 | 初步工艺判断 | 工程审 |
| Demand Repetition | 是否有多人表达类似需求 | 0-5 | cluster | cluster size/source diversity | cluster 审 |
| Competition | 竞争/替代品强度，分高代表竞争压力低 | 0-4 | 搜索/Kickstarter/Amazon/论坛 | 提取替代方案 | 行动前 |
| Contactability | 是否能合规联系到用户 | 0-3 | profile、public contact | 公开联系方式/站内回复可能性 | outreach 前 |

### 7.2 总分计算

```text
Raw Score =
Problem Severity * 1.2
+ Intent * 1.5
+ Urgency * 0.8
+ Existing Solution Gap * 1.0
+ Suppression Reason * 1.2
+ Budget Signal * 1.0
+ External Help Probability * 1.5
+ Manufacturability * 0.8
+ Demand Repetition * 1.0
+ Competition * 0.6
+ Contactability * 0.8
```

归一化：

```text
Demand Score = round(100 * Raw Score / Max Raw Score)
```

置信度调整：

```text
Priority Score = Demand Score * Evidence Confidence * Source Reliability
```

其中：

- Evidence Confidence：0.4-1.0，由证据完整性决定。
- Source Reliability：0.6-1.0，由来源类型决定。项目日志/明确询价 > 普通评论 > 搜索 snippet。

### 7.3 进入下一步阈值

- `Priority Score >= 70`：人工审核并考虑 outreach。
- `50-69`：进入 cluster，不单独联系。
- `< 50`：暂存，不行动。

10k probe 后新增硬性过滤：

- HN 中 `Launch HN`、`Who is hiring`、新闻讨论、行业评论，只能进入 market pattern，不进入 outreach queue。
- StackExchange 中纯技术问答只能作为 blocker/RFQ 学习样本；只有明确 prototype、production、supplier、budget、quantity、external help 的项目才进入 lead queue。
- 进入 outreach 前必须有人看过原帖上下文和作者可联系性。

### 8.3 一个人的需求能不能扩展成 Demand Cluster？

可以，但不能直接假设可以。单个需求只能作为 seed。要扩展成 Demand Cluster，必须满足：

- 语义相似：相同 problem/use_case，而不只是关键词相似。
- 用户独立：>= 8 个 unique users，不能是同一作者多次发帖。
- 来源多样：最好跨 >= 2 个来源。
- 时间分布：不是同一天同一热点导致的噪声。
- 共同未满足原因：例如都卡在小批量外壳、防水、SMT、定制传感器。
- 行动信号：cluster 内至少一部分有 Intent 或 External Help。

如果只找到一个人的需求，下一步不是立刻定义产品，而是：

1. 用 seed 生成 20-50 个搜索 query。
2. 反向搜索类似表达。
3. 搜索现有解决方案和竞品。
4. 判断是否有重复需求和未满足原因。
5. 没有重复证据则只能作为个案 lead，不作为市场机会。


### 9.4 缺失信息检测

必须检测：

- 目标用户和使用场景是否明确。
- 功能是否可测试。
- 数量级是否明确。
- 预算或价格敏感度是否明确。
- 尺寸、外观、安装方式、环境要求是否明确。
- 是否涉及电池、无线、医疗、安全、儿童、食品接触等高风险。
- 是否有参考产品/草图/CAD/BOM。
- 是否需要认证。

### 9.5 自动生成 Clarifying Questions

规则：

- 最多 8 个问题。
- 先问影响报价最大的。
- 不问工程师自嗨问题。
- 每个问题都说明为什么影响报价或可行性。

例：

```text
1. First prototype quantity: 1, 5, 10, or 50 units?
2. Where will the device be used: indoor, outdoor, wet, high temperature, wearable?
3. Do you need a working prototype only, or a design ready for small-batch production?
4. What is the rough target budget per prototype and per production unit?
```

### 9.6 人工审核节点

- Outreach 前：确认需求不敏感、不违法、不高风险。
- 访谈后：确认用户意图和预算。
- RFQ 前：确认技术假设没有过度脑补。
- 供应商回复后：确认报价范围和风险。
- 客户报价前：确认毛利、时间、责任边界。

## 11. 真实交易验证 SOP

### 11.1 进入联系用户条件

满足任意两个：

- Priority Score >= 70。
- 用户表达明确 Intent 或 Purchase Intent。
- 有外部帮助信号。
- 有预算/数量/时间信号。
- 需求属于有效 cluster。
- 可找到合规公开联系方式或允许站内回复。

不得联系：

- 未成年人、医疗高风险、武器/违法/监控滥用需求。
- 私密数据来源。
- 只能通过违反平台规则触达的用户。

### 11.2 AI 背景研究

输入：用户公开 profile + 原帖 + 相关项目。

输出：

```json
{
  "user_context": "string",
  "project_context": "string",
  "likely_stage": "idea|prototype|blocked|sourcing|buying",
  "likely_pain": "string",
  "evidence": ["string"],
  "recommended_angle": "string",
  "risk_flags": ["string"]
}
```

### 11.3 第一封消息模板

原则：短、具体、引用对方原始需求、不假装熟人、不夸大能力。

```text
Hi [Name],

I saw your post about [specific need/problem]. It sounds like the hard part is not just the idea, but turning it into a manufacturable prototype / finding the right supplier for [specific part].

We are a small China-based hardware team testing whether we can help people turn early hardware requirements into supplier-ready RFQs and real prototype quotes.

If this is still active, I can help you sanity-check the requirement and see whether it is quoteable. No need to commit to anything.

Would it be useful if I send 5-6 clarifying questions based on your post?
```

### 11.4 访谈问题生成

访谈目标不是“用户喜不喜欢”，而是判断是否进入真实项目。

问题：

1. 你现在为什么需要这个硬件？
2. 过去尝试过什么方案？
3. 为什么现有方案不行？
4. 你现在卡在哪一步？
5. 你已经投入了什么：时间、钱、原型、CAD、代码、供应商沟通？
6. 如果可以做 prototype，你期望数量、时间、预算是多少？
7. 你是否愿意为了明确报价提供更多需求信息？
8. 如果报价合理，你是否愿意支付定金启动？

### 11.5 访谈记录

```json
{
  "lead_id": "string",
  "date": "datetime",
  "participants": ["string"],
  "problem_confirmed": true,
  "intent_level": "intent|purchase_intent",
  "budget_range": "string",
  "timeline": "string",
  "decision_maker": true,
  "next_step": "stop|more_info|rfq|quote|deposit",
  "notes": "string"
}
```

### 11.6 进入 RFQ 条件

必须同时满足：

- 问题真实。
- 用户愿意提供需求信息。
- 项目不违法、不高风险。
- 初步技术上可制造。
- 有数量/预算/时间至少两个维度的信息。
- 用户接受“报价后如果合理需要定金”的交易逻辑。

### 11.7 停止条件

- 用户只是免费咨询，不愿提供信息。
- 没有预算，也不愿讨论预算。
- 需求技术风险明显超出能力。
- 供应商难以报价且用户不愿澄清。
- 客户拒绝任何付款承诺。

### 11.8 要求付款条件

- 已确认范围。
- 已有供应商报价或可信成本估算。
- 已明确 deliverable。
- 已说明不包含项和风险。
- 客户口头接受价格和时间。

付款建议：

- 早期 prototype：30%-50% 定金。
- 小额研究/RFQ 服务：可先收 fixed discovery fee。
- 不接受“先做完整方案再决定是否付款”。

## 15. Day 1 / Day 3 / Day 7 执行计划

### Day 1：验证世界上是否有可抓取需求

目标：拿到第一批 raw data 和 demand candidates。

Person 1：

- 定义 50 个 seed queries。
- 选定 5 个 Reddit/论坛社区、20 个 GitHub 查询、20 个 YouTube 查询。
- 审核 AI 输出的 top 100 demand candidates。

Person 2：

- 定义硬件需求分类标准和 forbidden/high-risk 类目。
- 审核 50 条 AI 分类，修正 prompt。
- 建立 RFQ readiness 的人工判断标准。

Person 3：

- 核查数据源合规和账号/API key。
- 建立成本/时间记录表。
- 准备 outreach 模板和供应商搜索模板。

AI/脚本：

- 跑 10,000 条 raw items，但必须设置 source quota，避免单一来源填满样本。
- 输出 `demand_candidates.csv`。
- 生成 top 100 review queue。

Day 1 成功标准：

- 至少 10,000 条 raw items。
- 至少覆盖 4 个来源，每个主来源 1,000-3,000 条，不能只靠 HN/StackExchange。
- 至少 300 条 strict actionable candidates。
- 人工审核 top 100，确认 precision 初步 >= 50%。

### Day 3：得到第一批 Qualified Demand 和需求簇

目标：从数据中筛出可行动需求，并开始联系。

Person 1：

- 人工审核 top 200。
- 选出 30 个 high-priority leads。
- 发送 20-30 条人工审核后的 outreach。

Person 2：

- 对 top 20 QD 生成 structured requirement。
- 判断 10 个是否 RFQ-ready 或需要澄清问题。

Person 3：

- 对 5-10 个 RFQ-ready 或接近 ready 的需求搜索供应商。
- 每个需求找 5-10 个候选，人工筛 Top 3。

AI/脚本：

- 扩大到 10,000 raw items。
- 输出 `qualified_demands.csv` 和 `clusters.csv`。
- 生成用户背景研究、首封消息草稿、澄清问题。

Day 3 成功标准：

- >= 100 条 strict actionable candidates。
- >= 30 条 human-reviewed Qualified Demand。
- >= 3 个有效需求簇。
- 发送 >= 20 条 outreach。
- 至少 5 个需求生成初版 RFQ/澄清问题。

### Day 7：开始真实项目验证

目标：不是完成系统，而是让漏斗进入真实沟通、RFQ、供应商回复。

Person 1：

- 完成 5-10 个用户沟通/异步问答/访谈。
- 判断哪些进入 RFQ，哪些停止。

Person 2：

- 对 3-5 个需求完成 RFQ-ready 文档。
- 明确缺失信息、风险和报价边界。

Person 3：

- 向 10-15 家供应商发送 RFQ。
- 获得至少 3 个有效供应商回复，争取 1 个报价。
- 对 1-2 个客户给出真实报价或报价区间。

AI/脚本：

- 持续记录漏斗转化率、成本、人力时间。
- 生成第一周实验报告。

Day 7 成功标准：

- 10,000+ raw items。
- 100+ Qualified Demand。
- 3+ Demand Clusters。
- 20-30 outreach sent。
- 5+ positive replies / continued conversations。
- 3-5 RFQ drafts。
- 10+ supplier RFQs sent。
- 3+ supplier responses 或 1+ quote。
- 至少 1 个客户进入明确报价/定金讨论。

Day 7 失败也有价值。如果失败，需要明确是哪一层失败：

- 公开需求密度不够。
- AI 识别 precision 不够。
- 用户不回复。
- 用户无预算。
- RFQ 生成不可用。
- 找不到供应商。
- 供应商不愿接。
- 报价后客户退出。
- 人力成本过高。

### 18.4 对原计划的修改

#### 修改 1：新增漏斗层级

原计划容易把 `Demand Signal` 和 `Qualified Demand` 混用。现在必须拆成：

```text
Raw Item
```

#### 修改 2：Day 1 不再只要求 1,000-3,000 条

实测 10k 在几分钟内可跑完，所以 Day 1 应直接跑 10k。但必须有 source quota。

建议 Day 1 quota：

```text
GitHub Issues/Discussions/Repos: 2,000

YouTube or public web search: 500
```

如果 Reddit/YouTube 暂无 API key，则用 GitHub + Discourse + search API 补齐，不要让 HN 自动填满样本。

#### 修改 3：HN 降级为市场模式发现，不作为首批 outreach 主渠道

HN 有价值：

- Ask HN 中有真实硬件创业/制造问题。
- 评论里有供应链、制造、prototype 经验。
- 适合识别 market pattern 和 blocker。

HN 的问题：

- 噪声高。
- 很多是历史讨论、招聘、Launch、行业评论。
- 很难把评论作者直接转成 lead。

因此：

- HN 进入 cluster / blocker analysis。
- 只有 `Ask HN` 或强第一人称项目帖进入 outreach queue。

#### 修改 4：StackExchange 适合 RFQ/技术断点学习，但非 maker 需求不足

StackExchange 强项：

- PCB、SMT、认证、DFM、BOM、prototype、manufacturing blocker 很密集。
- 很适合训练 Demand → RFQ 和 blocker taxonomy。

弱项：

- 用户多是 maker/engineer/technical founder。
- 不足以证明“普通消费者/小企业主”的非 maker 需求。

因此 H-A2 不能靠 StackExchange/HN 证明，必须补 Reddit、YouTube 评论、行业论坛、小企业场景搜索和访谈。

#### 修改 5：成功阈值调整

原 H-A1 “10,000 条内容中 >= 150 条硬件需求信号”过低。实测宽松 demand signal 很容易超过，但严格 actionable lead 才有意义。

更新建议：

```text
Demand Signal success:
>= 1,000 / 10,000 raw items

Strict Actionable Candidate success:
>= 300 / 10,000 raw items

Human Reviewed Qualified Demand success:
>= 30 / 10,000 raw items after top-100 review
```

H-D1 更新为：

```text
Qualified Demand / 1,000 sources
```

必须明确这里的 Qualified Demand 是人工审核后的 QD，不是规则候选。

#### 修改 6：必须增加人工 top-100 review

规则分类可用于排序，但不能直接触发 outreach。每轮实验必须：

1. 输出 top 100。
2. 人工标注 `qualified / not qualified / unsure`。
3. 记录误杀和误报原因。
4. 用标注结果修改 prompt/规则。

#### 修改 7：聚类不能只按关键词桶

本次 rule cluster 显示：

```text
Sensors / IoT
Manufacturing / supplier
PCB / assembly
Enclosure / mechanical
Arduino / ESP prototype
Robotics / motors
Raspberry Pi device
```

这些只是关键词桶，不是 Demand Cluster。正式计划中 cluster 必须满足：

- 同一用户问题。
- 同一未满足原因。
- 同一制造/RFQ路径。
- 多用户、多来源重复。

例如 “PCB / assembly” 太宽，不是市场机会；“软件工程师做低量蓝牙消费设备，卡在 FCC/SMT/外壳小批量” 才可能是 cluster。

### 18.5 下一轮实验优先级

下一轮不是继续扩大 HN/StackExchange，而是补齐来源偏差：

1. GitHub Issues/Discussions：验证真实项目和开源硬件卡点。
2. Discourse / maker forums：验证 prototype blocker。
3. Reddit：验证非 maker 和普通需求，需要先处理 API/合规。
4. YouTube 评论：验证 creator/maker audience 的需求表达。
5. Public search：寻找小企业/行业场景。

### 18.6 目前对总假设的初步判断

本次 probe 支持：

- H-A1：公开互联网中确实有大量硬件需求信号。
- H-A3：未满足原因和卡点信号明显存在。
- H-C2：DIY/原型到制造之间存在大量 PCB、SMT、认证、外壳、供应商断点。
- H-D1：低成本公开数据发现是可行的。

本次 probe 不能证明：

- H-A2：需求是否超出 maker/engineer 圈层。
- H-B1：AI 是否真实激活新增硬件需求。
- H-C4/F1/F2/F3：用户是否信任、接受报价、付款。
- H-G3：单项目经济模型是否成立。

因此，原计划方向不需要推翻，但必须更严格：

> 第一阶段不是“找到很多硬件相关内容”，而是“从 10k 公开内容中稳定找到 30+ 人工确认的可联系 Qualified Demand，并推动其中 5+ 进入真实沟通”。

### 19.2 关键结论

#### 结论 1：数据量不是瓶颈，噪声和来源质量才是瓶颈

100k 中有 14,587 条宽松候选，但 v2 strict actionable 只有 175 条。说明：

```text

```

后续不应继续追求 raw volume，而应追求 source-level QD density。

#### 结论 2：HN 适合发现模式，不适合直接获客

HN 里确实能发现高价值 Ask HN 模式：

- first hardware startup
- get health tracker manufactured
- hardware product to market
- electronics enclosure manufacturer
- finding manufacturers

但 HN 的大量评论、新闻、Launch、招聘、行业讨论会制造误报。HN 应进入：

- market pattern
- blocker taxonomy
- query seed
- RFQ training examples

不应作为第一批主要 outreach source。

#### 结论 3：最稳定痛点是 prototype to production，不是“创意本身”

最反复出现的断点：

- 已有 Raspberry Pi / Arduino / dev board prototype，但想做 proper version。
- 不知道如何找 manufacturer / supplier。
- 小批量制造太贵或不透明。
- PCB assembly、SMT、DFM、BOM、认证、外壳卡住。
- 对中国供应链感兴趣，但不知道怎么沟通和控风险。

这说明第一阶段更应关注：

> 已经行动过、卡在制造/外壳/认证/供应商的项目。

而不是泛泛收集“硬件创意”。

#### 结论 4：外壳 / 机械件比预期更重要

Strict actionable 中 `Enclosure / mechanical` 有明显信号。供应商网络不能只围绕 PCB / SMT，第一批至少需要：

- PCB / SMT
- 3D printing
- CNC
- 小批量外壳
- 简单装配
- 认证/测试顾问

#### 结论 5：AI 激活信号没有自然凸显

100k 泛爬里没有自然证明：

> AI 确实让更多人开始尝试做硬件。

AI 词很多，但多数是泛 AI 讨论，不是“AI 让我开始做硬件”的证据。H-B1 需要单独实验：

- ChatGPT / Claude / AI + PCB / Arduino / prototype 专门查询。
- GitHub / YouTube / build logs。
- 访谈作者确认“没有 AI 是否会开始做”。

#### 结论 6：非 maker 需求仍未被证明

当前样本仍偏技术创业者、软件工程师、maker。不能证明普通消费者、小企业主、非技术用户正在大量产生硬件需求。H-A2 需要：

- Reddit 官方 API / search
- YouTube comments
- 小企业/行业论坛
- public search / Common Crawl
- 真实访谈

## 20. 1M 普通用户 / 隐性硬件需求校准

执行时间：2026-08-21 / 2026-08-22

用户提醒了一个关键盲点：普通用户、小企业主、物业/餐饮/宠物/家庭用户不一定会说 `hardware / sensor / device`。他们可能只是说“需要一种办法”“怎么知道某个东西满了/坏了/太热了/没关/丢了”“不想人工检查”。因此 1M 实验不能只抓显性硬件词，还要识别隐性物理世界需求。

详细阶段报告：

```text
mvp_probe/data_1m/1m_nonmaker_latent_findings.md
mvp_probe/data_1m_commoncrawl_v4_latent_forums/probe_summary.md
mvp_probe/data_1m_commoncrawl_v5_physical_latent/probe_summary.md
mvp_probe/data_1m_targeted_cc_v2/probe_summary.md
```

### 20.1 已完成校准结果

#### Random Common Crawl v4：宽松隐性规则

```text
Raw records sampled: 200,000
Candidates retained: 170
Strict candidates: 96
Latent physical need candidates: 67
Candidate/raw: 0.08%
Strict/raw: 0.05%
```

样本问题：大量 SaaS、营销页、产品目录、银行/医疗/物流页面、技术文档。`keep track of / monitor / alert / app / system` 在普通网页里误判严重。

#### Targeted Common Crawl：行业/社区 URL

```text
Raw pages fetched: 952
Candidates: 1
Strict candidates: 0
Latent physical need candidates: 0
Candidate/raw: 0.11%
Strict/raw: 0.00%
```

问题：Common Crawl CDX 可以定向域名/URL pattern，但实际命中经常是列表页、帮助页、营销页，不是用户 thread。仅靠 URL pattern 不能保证抓到真实发问内容。

#### Random Common Crawl v5：物理对象锚定规则

```text
Raw records sampled: 40,592
Candidates retained: 9
Strict candidates: 3
Latent physical need candidates: 1
Candidate/raw: 0.02%
Strict/raw: 0.01%
```

v5 新增 `physical_object_hits` 和 `digital_noise_hits`，要求隐性需求必须有物理对象/状态锚点，例如 freezer、tank、bin、pallet、tool、door、vehicle、medicine、soil、water、temperature、humidity。收紧后噪声明显下降，但随机网页召回几乎消失。

### 20.2 关键结论

#### 结论 1：用户可以不说硬件，但必须有物理对象/状态

错误判断：

```text
need + track/monitor/alert = latent hardware demand
```

新判断链：

```text
用户/场景
-> 物理世界对象或状态
-> 需要监测、提醒、计数、定位、控制、记录
-> 当前做法是人工检查、事后发现、买不到、太贵、不适配
-> 可能需要装置、传感、执行器、外壳、安装、集成
```

例如，不需要出现 `sensor` 也可以保留：

```text
I need a way to know when the freezer gets too warm.
How can I tell when the trash bin is full without checking it?
We need to track tools in the shop.
Is there something that alerts me when the water tank is low?
I want to know if the gate was left open.
```

但如果没有物理对象/状态，应强降权：

```text
track order
monitor Kubernetes
keep track of invoices
notify me when a record is listed
dashboard alert
```

#### 结论 2：普通用户隐性需求比 maker 需求更难抓

maker/HN/GitHub 样本偏圈层，但需求表达更清楚：prototype、PCB、enclosure、manufacturer、small batch、certification。普通用户样本更接近真实大众场景，但他们写的是生活/运营问题，不是产品规格；如果 source 不是 thread/comment/question，信噪比会非常低。

#### 结论 3：Random Common Crawl 不适合作为 1M 主采集源

Random Common Crawl 可以继续作为：

- 负样本训练集。
- source density 估计。
- 长尾行业页面补充。

但不应作为主获客或主验证来源。继续硬跑到 100w 只会增加人工审核成本，无法解决“抓到的不是用户发问内容”的结构性问题。

#### 结论 4：`track / monitor / alert` 已高度软件化

这些词在 SaaS、银行、物流、Kubernetes、dashboard、订阅提醒、电商上架通知中极常见。它们不再是硬件需求强信号，必须和 physical object、manual workaround、purchase/build intent 共现。

### 20.3 对原计划的修改

#### 修改 A：1M source quota 改成 thread-first


硬约束：

- maker/HN/GitHub/StackExchange 合计不超过 8%-10%。
- 单一域名不超过 5%。
- 每个 source 单独报告 raw -> candidate -> human-reviewed QD -> outreach lead -> RFQ candidate。
- 没有 API 或合规路径的来源，不绕过登录、验证码、反爬或付费墙。

#### 修改 B：新增隐性硬件需求标签

每条候选增加：


#### 修改 C：人工审核问题改写

人工审核不问“有没有硬件词”，而问：

在 API/source 准备前，不建议继续盲跑 100w。下一步应先完成：

```text

2. 20-30 个高价值行业论坛 sitemap/thread 列表
3. 每个 source 先跑 1k-5k，小样本人工审 50-100 条
4. source precision 低于 10% 的来源停止扩量
5. precision 高于 30%-50% 的来源才进入 100k/1M 配额
```

### 20.4 当前对总假设的影响

本轮不推翻 AI+硬件机会假设，但明确否定一个执行路线：

> 不能靠“硬件关键词 + 随机网页扩量”证明普通用户需求。

更合理的路线是：

> 用普通用户 thread/comment/question 抓取“物理世界问题”，再用人工/LLM 判断它是否可转化为装置、集成、制造或供应链需求。

当前需要降权或人工复核的词簇：

```text
vision / sound / biometric 过泛，容易命中视频、音频、AI/媒体语境。
power device / home device 召回高，但语义过宽，需要加具体场景或信号。

```

阶段性判断：

```text
产品结果倒推是有效的，但不能直接把所有产品名变成 query。
有效的是“产品 -> 动作词/场景词/信号词”的反推：
monitor / track / alert / detect / measure
home / small business / pet / security / vehicle / farm
temperature / water level / air quality / motion / location
```

下一步建议：

```text

2. 对高产 RFQ query 抽 100 条人工复核，测 RFQ-ready precision。
3. 实时 Reddit 抓取降速重跑，只跑 50-80 个最高价值 query，不做全 subreddit 笛卡尔积。

```

## 27. 方法论调整：产品宇宙驱动机会发现

新增执行方案：

```text
E:\AIHardware\假设验证研究\产品宇宙驱动机会发现执行方案.md
```

本节调整主路线。旧路线是：

```text
人工猜关键词
-> 爬需求
-> 找硬件机会
```

新路线是：

```text
产品宇宙
-> 产品语义理解
-> Problem Space 抽取
-> 语义扩展
-> 全网需求信号
-> 趋势和供需缺口
-> 机会假设
```

这意味着：

```text
1. 不再一开始人为定义“应该抓什么硬件领域/装置/关键词”。
2. 先从 Kickstarter / Indiegogo / YouTube / Product Hunt / Maker 社区等真实产品/项目平台建立 product universe。
3. 让 AI 自动抽取产品类别、功能、目标用户、使用场景、解决的问题、硬件复杂度、AI claim。
4. 从产品背后的 problem space 自动扩展用户问题表达，而不是从产品名硬派生 query。
5. 再去 Reddit / YouTube 评论 / 论坛 / 搜索结果找 complaint / DIY / 求助 / 需求信号。
6. 最后比较 Problem Demand vs Existing Product/Supply，找异常区域。
```

新的核心对象：

```text
Product Object
Problem Object
Demand Signal Object
Problem Space Graph
Semantic Query Bank
Supply-Demand Gap Metrics
```

优先测的异常：

```text
Problem discussion grows fast, product count low.
Product count high, complaints remain high.
DIY workaround high, polished product low.
RFQ/manufacturing questions high.
AI claim high, real AI activation low.
```

现有脚本定位调整：

```text
build_product_reverse_catalog.py
  从规则产品抽取升级为 product_universe_builder。

curate_reverse_queries.py
  从 query 清洗升级为 semantic_query_bank_builder。

offline_validate_reverse_queries.py
  从规则匹配升级为 demand_signal_matcher。

probe_product_reverse_reddit.py
  从全量笛卡尔搜索改为按 problem space 分批验证。
```

下一轮不直接继续 100w 抓取，而是先跑 `v2_product_universe` 小闭环：

```text
1. 用现有 17,073 条 Kickstarter/Indiegogo 产品作为 seed。
2. 增加 YouTube / Product Hunt / Maker 项目入口，补到 30k-50k product universe。
3. 对 2,000 条产品做 AI/规则混合抽取，生成 problem_space_seed。
4. 聚类出 30-80 个 problem spaces。
5. 每个 problem space 自动生成 20-50 个 problem-first query。
6. 用已有本地语料 + 小规模 Reddit/YouTube 评论验证。
7. 输出第一版 supply-demand gap 排名。
```

成功标准：

```text
至少发现 20 个未由我们人工预设的 problem spaces。
每个 problem space 同时有产品证据和需求文本证据。
至少 5 个 problem spaces 显示“需求增长/抱怨/DIY 高于产品供给”的异常。
人工抽样 precision 不低于：
- product semantics: 75%
- problem signal: 60%
- latent hardware demand: 40%
- RFQ-ready signal: 30%
```
